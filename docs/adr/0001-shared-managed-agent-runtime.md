# ADR 0001: Shared managed-agent runtime

## Context

Summit's Go API and PostgreSQL are the authority for authenticated users, user-owned projects, agent configuration, lifecycle, quotas, and billing. Rivet and Pi Durable are TypeScript-oriented runtime components. The existing Go orchestrator consumes deployment/build outbox work, and the platform uses gVisor for isolated build workloads.

The runtime must support independent conversations, survive process restarts, and keep customer code and credentials out of shared control-plane processes. Rivet's production storage and recovery guarantees, cross-worker recovery, and security boundaries have not yet been proven in Summit's deployment topology.

## Decision

For the first managed-agent slice, run one shared Rivet runtime for Summit users, mapping **one Rivet Actor per Summit session**. Each session actor owns exactly one Pi Durable root conversation. This adopts the documented Gate 1 fallback after review verified that pinned `@earendil-works/pi-durable@1.4.0` has no supported conversation deletion API; attempting to co-locate multiple sessions in one deployment Actor prevents isolated conversation deletion/purge without raw SQLite mutation.

The session actor is keyed by a versioned 4-element tuple generated by the control plane:
```text
["summit-agent-v1", project_id, deployment_id, session_id]
```

Keep Go as the public control plane and owner of platform metadata. Add a Go outbox handler and authenticated TypeScript adapter for managed-agent events. Do not give the adapter direct PostgreSQL access or expose Rivet credentials to the dashboard.

Keep per-actor serialization in the session actor for ordered submissions within that session. Go's durable `deployment_queue_seq` remains authoritative for deployment-wide admission and FIFO ordering across session actors.

Use the tested destruction/purge lifecycle: deleting a session calls the actor's `destroy` action, which calls `c.destroy()`. Rivet's `onDestroy` lifecycle callback closes the Pi Durable harness and then removes that actor's SQLite file, WAL, and SHM. Use only public Rivet and Pi APIs; never issue raw SQLite DELETE SQL.

Use one fresh gVisor sandbox per run attempt for code execution. Do not execute customer code in the Go API, adapter, or Rivet worker. Resolve model credentials through a scoped gateway and deliver any approved one-purpose sandbox capability directly to the sandbox. A shared worker process is infrastructure reuse, not a user, credential, or code-execution boundary.

The account model remains Summit users owning projects. Agent definitions, revisions, deployments, sessions, runs, credentials, and sandbox references are scoped to `user_id` and `project_id`. This decision adds no organization ownership model.

## Alternatives considered

- **Dedicated Rivet runtime for every Summit user:** Stronger infrastructure separation, but adds deployment, storage, upgrade, and support overhead before runtime demand is known. Not selected for the initial slice.
- **One Actor per agent deployment with N Pi conversations:** Evaluated as the initial Gate 1 hypothesis. Rejected because pinned Pi Durable 1.4.0 has no conversation deletion API, preventing isolated session deletion and storage cleanup without unsupported raw SQL manipulation of internal Pi tables.
- **One Actor per session:** Selected. Provides clean 1:1 mapping between a Summit session and a Pi root conversation, enabling granular session actor destruction and clean per-session SQLite file purging.
- **One deployment Actor with one shared transcript:** Rejected because users' sessions would share context.

## Consequences and constraints

- Every public operation must authorize through the owning user and project. Actor keys are generated by Summit and are not authorization tokens.
- V1 limits a deployment to one active run and queues accepted runs FIFO across its sessions. This avoids concurrent Pi and sandbox work until the PoC validates stronger limits.
- Rivet action parallelism must not be treated as run ordering. Summit's durable `deployment_queue_seq` in Go/PostgreSQL is the authoritative admission rule across sessions.
- No multi-worker availability claim is allowed until actor placement, storage acknowledgements, failure recovery, backup/restore, and measured RPO/RTO are tested.
- Pi Durable is beta and roll-forward-only. Pin exact compatible versions, test upgrades and restore, and do not run an older binary against newer actor state.
- External tool side effects need receiver-enforced operation IDs. Pi request deduplication does not guarantee exactly-once effects.
- Sessions, revisions, and actor cardinality remain subject to the Gate 1 results recorded in [`managed-agents-spec.md`](../managed-agents-spec.md).

## Gate 1 acceptance

Before migrations or public API work, prove independent session state and deletion, concurrency limits, actor worker recovery, storage topology, Pi tool/model replay behavior, credential isolation, and a per-attempt gVisor sandbox. Record dependency versions and measured recovery objectives. Local Rivet Engine integration tests verify session actor transcript isolation and isolated destruction/storage purging. Multi-worker placement and cross-worker migration remain unverified and require cluster-level validation before production.
